# The 2026-10-C1 cohort: what it checks, and what it cannot yet

`config/cohorts/2026-10-C1/` is the MLPerf Endpoints submission cohort for the
`2026-10-C1` round, expressed in the `inference_endpoint.validation` dialect:

```
2026-10-C1/
├── cohort.yaml         the manifest: `ruleset_dir: ruleset`
├── valid_refs.yaml     every fact a row may name, as its document spells it
├── pareto.yaml         per-pareto checks
├── point.yaml          per-run checks
├── system.yaml         per-system checks
└── ruleset/            this cohort's catalog: models.yaml + datasets.yaml
```

Run it against a submission with:

```bash
python -m inference_endpoint.validation \
  src/inference_endpoint/config/cohorts/2026-10-C1 \
  path/to/submission
```

## What the cohort checks

- **Per run** (`point.yaml`): the §8.3 disclosure set is present with content
  (non-blank); the cohort and seed declarations are well-formed and match
  published set A (membership, the §4.6 adoption window, the two recorded
  runtime seeds); the recorded API key is omitted or redacted; warmup is
  declared, ordered, retained, and salted when it issued requests (§6.3.1); the
  run completed (`complete`); the summary cleared its concurrency duration tier
  (600 s at ≤32, 1200 s above, and 2400 s above for agentic runs); a
  fixed-concurrency run declares a positive concurrency and reports a positive
  TPOT P90 (the dedicated Offline run is exempt from both, §6.5) while the
  dedicated Offline run declares the `max_throughput` load pattern; the summary
  carries output tokens and at least the dataset's §12 acceptance count; at
  least one accuracy result is present; a dedicated Offline run meets §5.7.2
  through `derived.offline_ordering`.
- **Per pareto** (`pareto.yaml`): §5.6's point cap; §5.3's point-count minimum;
  §5.4's mandatory-region coverage; §5.7's Offline presence (`derived.agentic`
  picks the expected direction); mandatory-region and Offline accuracy coverage,
  per-region result cardinality, exclusion of choice-point carriers, and
  non-empty accuracy documents; `pareto_accuracy_gate` carries the §15 gates; an
  empty accuracy entry list fails `pareto_accuracy_result_entryless`. No point
  may fall outside every region including the margin
  (`derived.out_of_range_points`); §8.1's model-name/directory agreement
  (`pareto_model_name_consistency`); §9.1/§4.5.3's per-point node declaration,
  maximal engagement and `system_tps_per_kw` denominator (`pareto_nodes_used`,
  `pareto_maximal_engagement`, `pareto_tps_per_kw`).
- **Per system** (`system.yaml`): the §4.5.2 power declaration is present
  (advisory) and its `power_method` is Appendix E vocabulary.
- **Vocabulary** (from `valid_refs.yaml`): an `offline` value outside §8.3's
  three, a `region` outside its six, a steady-state verdict/status outside §4.4,
  a `load_pattern` outside §6.1 and a value of the wrong type are refused at
  collect time, so they are not repeated as rows; the facts the client's summary
  writes as `null` (`qps`, `duration_ns`, `e2e_avg_interactivity`,
  `output_sequence_lengths_full_run`) are declared `nullable: true`.

## Not yet expressible

The dialect decides a row from one node's facts plus the pareto's named
derivations (`derived.*`). The rules below need more than that; each is a
candidate for a new derivation or operator, not something a row can fake:

| Rule (as the CLI names it)                                                                           | Why a row cannot decide it today                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agentic inline aliases (§4.3)                                                                        | `agentic_combined` entries are inline performance scores, excluded from validation coverage, cardinality and gating. Inline-only documents are nonempty and fill no required band. An inline score under another dataset alias cannot be told apart from validation results by these artifacts.                                                                                                                                                                                         |
| Steady-state basis (the window as the §6.2 duration basis, per-region floors, drifting-metric lists) | the status/verdict vocabulary and §4.4's official-reading alias are checked (`point.result_summary.steady_state`, the tree's `system_tps`); the checker's own `steady-state-basis`/`point-duration` flags are warn-level basis notes (never rejections), so only warn-level gaps remain: the duration rows compare whole-run `duration_ns` against the 600 s/1200 s split rather than the window's `duration_s` against the per-region floors, and the drifting-metric list is not read |
| Server-side streaming, warmup log archives, power-source verifiability                               | explicitly not artifact-derivable (the CLI documents the same limits)                                                                                                                                                                                                                                                                                                                                                                                                                   |

What the loaders already refuse -- a missing
`system_desc.json`/`result_summary.json`/`point.yaml` fact, a `<system>/` with
no models, a pareto with no runs, an entry no scope can reach below the pool
root, a `c_min_override` Section 5.4 rejects, points disagreeing on
`max_supported_concurrency`/`c_min_override` -- needs no row here; those are
per-submission refusals, reported in the verdict block and counted at exit 1. A
malformed cohort table, or a listing refusal at the pool root itself, stops the
whole run before any check (exit 2).

## Known rough edges in this version

- The §12 floor rows key on `dataset_name` values spelled the way the submission
  checker's table spells them (`cnn_dailymail`, ...). A submission that spells a
  dataset differently gates the row off; extend the `when` list as spellings
  appear, or align the spelling.
- Vocabulary-only rules live in `valid_refs.yaml`: a value outside an allowlist
  is a collect-time refusal naming the offending tuple, counted separately at
  exit 1; its siblings remain judgeable. At least one failed finding yields the
  same process exit, while cohort/input-level faults prevent judging and exit 2.

- `derived.agentic` reads the catalog's `agentic` flag for the declared
  `model_name`; with no catalog entry (or an unknown model) it falls back to the
  declared shape -- an `offline` declaration reads as non-agentic, its absence
  as agentic -- so an unlisted model keeps the old inference.
- Set A publishes a third seed, `model_seed: 9315206023656308754`, that no
  client artifact records (its purpose is undocumented in the policies, and the
  client's ruleset pin deliberately omits it). Checking it needs a server-side
  artifact the submission does not ship, so no row reads it.
- `point_warmup_unsalted` cannot tell which dataset the warmup drew on; it keys
  on the declared salt once warmup issued requests. The CLI warns on an explicit
  `true` (salting only helps when server-side KV reuse is disabled), the
  opposite reading.
- The duration tiers read the whole run's `result_summary.duration_ns`; §4.4's
  basis is the steady-state window span
  (`point.config.steady_state.window.duration_s`), which no row reads yet. A
  whole run is never shorter than its window, so the tiers cannot false-fail,
  but a run whose window is short while the whole run clears the tier passes.
- `system_tps` is read the way §4.4 scopes the metric: the steady-state window's
  TPS (`result_summary.steady_state.tps.system`) where the summary carries a
  valid window, the whole-run `tps` otherwise; `full_run_system_tps` names the
  whole-run value explicitly.
- Accuracy gates are enforced at the cumulative level (see the table above):
  `pareto_accuracy_gate` joins the catalog's `accuracy_targets` with the
  `accuracy_datasets` tie and fails a run whose sample-weighted score falls
  below `factor x reference` or whose issued samples miss the minimum count.
  Per-set `targets` are populated only where a reference threshold is published
  -- none is for this round's models -- so only the cumulative gates exist.

- Percentile blocks are keyed by spelling: writers emit `"90.0"` where a row
  names `…percentiles.90`. `resolve` reads a numeric component against a key
  spelling the same number (the submission checker's canonicalisation), so the
  row finds it; a non-numeric percentile name would need its own row.
