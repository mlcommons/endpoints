Steady-State Detection

How steady_state_diagnostics.py decides whether a benchmark run reached a stable operating point — end to end, with worked examples and the math for each gate.

The problem in one sentence. A load-generator run ramps up, (hopefully) settles into a flat operating point, and may later degrade. We want to find the first stable plateau, report throughput/latency over exactly that window with an honest confidence interval, and refuse to certify a plateau that is real but too brief to trust.
Scope — single-turn, non-agentic only. This detector targets single-turn inference workloads; the current validation set is DeepSeek-R1 and GPT-OSS. It is not ready for multi-turn agentic workloads: the agentic per-super-pass throughput signal (NATL) is experimental, unvalidated, and prints a NOT-YET-SUPPORTED banner. Do not use agentic output for submission decisions.

0 · Vocabulary

TermMeaning
super-passA contiguous block of dataset_size samples in issue order — one analysis window. The atomic unit of the analysis — every metric becomes a per-super-pass series. Think of it as one "batch" for batch-means statistics.
metric seriesThe per-super-pass series of one metric percentile, e.g. tpot_p50 = [p50 of super-pass 0, p50 of super-pass 1, …].
gated metricsThe two that must be steady for a window to qualify: tpot_p50, tpot_p90 (decode-rate steadiness). TTFT is not gated — its high-concurrency tail variance is structural (prefill/ISL skew + queue), so it's tracked as a diagnostic and raises a soft drift warning, but never hard-fails a window. p99, sample latency, warm-turn TTFT are diagnostic too.
plateauA maximal run of super-passes that is trend-flat and low-variance for every gated metric. A run can contain several (a staircase).

1 · The pipeline

This is a post-run, offline analysis — a cold-path step that runs after a benchmark finishes, reading the recorded events.jsonl. It never touches the hot path. One pass over the log, then a fixed sequence of transforms. Each stage below links to its section.

  1. Parse & bucket Group performance-tracked samples into super-passes by issue order. → §2
  2. Reconstruct metrics Per sample: TTFT, TPOT, e2e latency, output tokens. → §3
  3. Adaptive warmup crop Drop leading super-passes still climbing toward the steady TPOT level. → §4
  4. Build metric series Per-super-pass percentile series for every tracked metric.
  5. Segment into plateaus Grow admissible windows left-to-right; each must pass the trend + CoV gate. → §5, §6
  6. Pick the reported plateau The first plateau that also clears the min-duration gate (§9); flag any later level shift. → §7
  7. Summarize + CI TTFT/TPOT percentiles, per-user & system TPS with batch-means intervals. → §8
  8. Minimum-duration gate Reject (or warn) if the window is too brief in wall-time to certify. → §9

2 · Bucketing into super-passes

The parser tracks only events between start_performance_tracking and stop_performance_tracking. Each sample.issued is assigned to super-pass issue_counter // dataset_size — so super-passes are issue-order blocks, not wall-clock windows. Retries refresh a sample's issue time but never re-bucket it or double-count TTFT.

Example: dataset_size = 4. Samples issued in order A,B,C,D,E,F,G,H,I →
ABCD
super-pass 0
EFGH
super-pass 1
I···
super-pass 2 (partial)

Each super-pass keeps: first/last issue timestamp (its offered-load span), last event timestamp (drain-inclusive), and the raw per-sample TTFT / TPOT / latency / token-count arrays.

3 · Reconstructing TTFT / TPOT / latency

From the three timestamps each sample emits (issued, recv_first, complete) plus its output text:

MetricDefinitionCaptures
TTFTrecv_first − issuedprefill + queue wait (interactivity)
TPOT(complete − recv_first) / tokens(output after the first chunk)steady decode rate
e2e latencycomplete − issuedwhole-request time (drives the relaxation term, §9)

TPOT needs a tokenizer to count output tokens, so --model (or --tokenizer) is required. Token counts use plain tokenization; the live aggregator uses the chat-template path, so absolute TPOT ms can differ for reasoning models — but CoV and trend tests are scale-invariant, so the steady/drift verdicts are unaffected.

4 · Adaptive warmup crop

The start of every run is a ramp: connections opening, caches filling, autoscale settling. A fixed crop either wastes good data or leaves ramp contamination. Instead the crop is data-driven:

  1. Take the driver series (tpot_p50 — TPOT ramps up to steady, monotone and clean).
  2. Estimate the steady level as the median of the back half of the run.
  3. Drop leading super-passes whose driver value is more than ±5% off that level — in either direction.
  4. Cap the crop at 50% of the run so it can never eat everything.

5 · The admissibility gate (trend + CoV)

Gate on TPOT only. Admissibility uses tpot_p50 and tpot_p90 — decode-rate steadiness. TTFT is not a hard gate: at high concurrency its tail is dominated by prefill time (tracking input-length skew) + queue wait, so its variance is structural (the TTFT tail ttft_p90 CoV stays high regardless of super-pass size) rather than un-steadiness (the TTFT tail ttft_p90 CoV floors at 0.3–0.9 regardless of super-pass size, while tpot CoV is ~0.01–0.03). This is empirical: on events.jsonl logs from GPT-OSS and DeepSeek-R1 across a range of concurrencies, gating on the TTFT tail fragmented runs whose decode was genuinely steady, while TPOT-only recovers them. TTFT stays a diagnostic and raises the soft drift warning (§7). The gate below therefore runs over the TPOT pair; the same trend + CoV logic applies.

A window [lo, hi) is admissible iff, for every gated metric, its per-super-pass series is (a) trend-flat and (b) within the loosest CoV bound. Two independent tests, because either can miss what the other catches.

5a · Trend test — Mann–Kendall with Hamed–Rao correction

Mann–Kendall is a rank-based (non-parametric) monotonic-trend test. For a metric series x₀…xₙ₋₁ it computes

S = Σ_{i<j} sign(x_j − x_i)     # +1 per rising pair, −1 per falling pair

then a tie-corrected variance Var(S), a continuity-corrected z = (S∓1)/√Var(S), and a two-sided p-value. Verdict is up/down only when significant at α = 0.05, else steady.

Flat window — [5.0, 5.02, 4.98, 5.01, 4.99, 5.0]
Rising and falling pairs roughly cancel → S ≈ 0 → z ≈ 0 → steady
Rising window — [4.0, 4.3, 4.6, 4.9, 5.2]
Every one of the 10 pairs is positive → S = 10 (max) → large z → up
The score, worked through (rising window). 
x = [4.0, 4.3, 4.6, 4.9, 5.2]     n = 5,  pairs = n(n−1)/2 = 10

S   = Σ_{i<j} sign(x_j − x_i)
    = +10        # all 10 pairs rising, none falling or tied

Var(S) = n(n−1)(2n+5)/18          # no ties
       = 5·4·15 / 18 = 16.67
z   = (S − 1)/√Var(S)             # continuity correction: S→S−1 since S>0
    = 9 / 4.08 = 2.20
p   = 2·(1 − Φ(2.20)) = 0.028     # two-sided; 0.028 < α = 0.05  → up
Flat window: rising and falling pairs cancel → S ≈ 0 → z ≈ 0 → p ≈ 1 → steady. Hamed–Rao then inflates Var(S) when the series is autocorrelated, shrinking z so serial correlation can't masquerade as trend.
Why Hamed–Rao? Neighboring super-passes are positively autocorrelated (a slow drift persists). Plain Mann–Kendall would under-count that correlation, shrink the variance, and cry "trend" on noise. The Hamed–Rao correction inflates Var(S) by the rank-autocorrelation, so only drift that survives the run's own persistence is called a trend. This is the default gate (mk_hamed_rao); four other algorithms (plain MK, Newey–West, Theil–Sen, slope-vs-scatter) run alongside as a corroborating panel shown in the diagnostics.

5b · Variance test — the CoV ensemble

Trend-flat is not enough: a window can be flat on average but jittery. So each metric series must also satisfy CoV = σ/μ ≤ bound. Rather than one bound, an ensemble {0.03, 0.05, 0.08} is used; admissibility only requires the loosest (0.08), while the diagnostics table shows which metrics clear the tighter ones. A window with fewer than 2 points is reported inconclusive, never PASS — so a micro-window can't masquerade as steady.

Flat window [5.02, 4.98, 5.01, 4.99, 5.00]: μ = 5.0, σ ≈ 0.0158 → CoV ≈ 0.0032 → clears all three bounds. ✔
Jittery window [4.8, 4.9, 5.0, 5.1, 5.2]: μ = 5.0, σ ≈ 0.158 → CoV ≈ 0.032 → clears 0.05/0.08, fails 0.03 — and its Mann–Kendall verdict is up, so it's inadmissible regardless. ✗

5c · Effect-size floor on trend breaks

The rank trend test is significance-only, and with enough super-passes it flags a practically negligible drift — a couple percent end-to-end — as a "trend." Left unchecked that over-fragments a genuinely steady run into many sub-window plateaus, none long enough to clear the duration floor (§9). So during segmentation a window breaks on trend only when the drift is both significant and practically large: |rel_drift| ≥ 0.05 end-to-end (OLS total change over the window median). Below that it's within noise and the window holds — CoV still guards genuine variance, so a truly choppy run still fragments; only over-sensitive trend breaks are relaxed.

Measured on the corpus. Fragmenting breaks had |rel_drift| ≤ 0.03; real drifts and level shifts ran 0.10–0.26 — a clean gap, so 0.05 separates them. With this floor a falsely-fragmented 15-min run collapses from 6 plateaus back to one 871s plateau and is reported, while a genuinely drifting run keeps its CoV/large-drift breaks and stays rejected.

6 · Plateau segmentation & the first-plateau rule

The gate implicitly segments the run. Segmentation grows a window from the left: from each start index, extend hi as far as the window stays admissible; the maximal admissible span is one plateau; then resume past it. A window straddling a staircase jump has high CoV and reads as a trend, so it breaks there — exactly the boundary we want.

The first plateau is the reported steady state — deliberately, even though a longest- or lowest-variance rule might pick a later one. Empirically the later steps of a staircase are degradation (a skewed long-output workload piling up, a worker going unhealthy), so the first healthy plateau is the representative number and the later steps are anomalies to flag, not to report.

One exception: the min-duration gate (§9) can skip a first plateau that is too brief to certify and report the next admissible one instead.

7 · Level-shift (staircase) detection

Reporting the first plateau must not silently hide that the run got worse. Alongside segmentation, a level-shift detector fires when two or more plateaus differ in pooled TPOT by more than the CoV band and a Pettitt change-point test (rank-based, pairs naturally with Mann–Kendall) confirms a single significant break in the per-super-pass TPOT means.

8 · Throughput & batch-means confidence intervals

Over the reported window:

TPS per-user = 1e9 / mean(TPOT_ns)                       # single-stream decode rate
TPS system   = Σ output_tokens / window offered-load span  # aggregate; issue-span denominator, NOT drain

The system-TPS denominator is the offered-load span (first issue → last issue), not the completion span — the drain after the last issue would inflate the denominator and deflate TPS on long-tail workloads.

Batch-means CI. Raw samples within a super-pass are autocorrelated, so a naïve iid interval is far too narrow. Instead each super-pass is one batch: take the per-super-pass means m₁…m_k, and SE = stdev(mᵢ)/√k, CI = grand_mean ± t₀.₉₅,k₋₁ · SE (Student-t, small-sample correct). The interval then reflects super-pass-to-super-pass variability — the thing that actually matters — instead of pretending every token is independent.

9 · Minimum-duration gate

Everything so far guarantees a window is statistically flat over ≥ MIN_TREND_N = 4 super-passes. But 4 super-passes is a count floor, and it is throughput-blind. When concurrency approaches the super-pass size (a c16k-scale submission), 4 super-passes drain in seconds — and no minutes-scale hiccup (KV-cache eviction, a slow autoscale, a sick worker) can possibly be observed in that time. A steady number measured over 2 seconds of a 2-hour run is not a steady state.

So the window must also clear a minimum wall-time, computed per window as the max of three terms, each covering a different regime:

min_duration = max( T_precision , T_relaxation , T_floor )

  T_precision  = k*·τ_sp (only if k* > MIN_TREND_N),  k* = max( ⌈(1.96·CoV_b / 0.05)²⌉ , MIN_TREND_N )
  T_relaxation = 5 · p90(sample e2e latency)                                    # queue / KV-eviction transient
  T_floor      = 600 s                                                          # MLPerf-style min-duration floor

τ_sp = median per-super-pass offered span, CoV_b = CoV of per-super-pass tpot_p50. The window's wall-time is its offered-load span (same denominator as system TPS).

Precision is exempt at the k* floor. When CoV_b is low enough that k* clamps to MIN_TREND_N, the metric isn't noisy and the ≥4 super-passes already meet the trend requirement, so precision is dropped from the max entirely. Without this, at exactly 4 super-passes k*·τ_sp = 4·τ_sp ≈ the window's own duration, so every minimal plateau would be flagged short regardless of wall-time — a clean 11-min plateau rejected on a technicality. Precision only binds once a genuinely noisy metric (k* > 4) needs more batches than the floor.

Why k* floors at MIN_TREND_N rather than a bigger constant: the batch-means CI already widens honestly when CoV_b is high, so k* self-raises where it matters; a larger floor would only over-penalize clean runs. The ×5 relaxation multiple is a literature-derived safety margin (relaxation time ≈ 1/(μ(1−ρ))), not fit from data.

Behavior: skip short plateaus, reject only if none qualify

By default the gate is part of window selection. Segmentation is walked in order and the first plateau that clears min_duration is reported — any earlier plateau too brief to certify is skipped, not reported. This is a deliberate exception to the first-plateau rule (§6): a plateau that is real but seconds long is not a steady state, so the reporter moves on. The headline notes the skip, and the level-shift baseline (§7) moves to the reported plateau so only degradations after it are flagged.

=== STEADY STATE (headline) ===
  window: super-passes 12..27 (post-warmup), 6400 samples
  note: skipped 2 earlier plateau(s) below min-duration; reporting plateau 3 of 5
  TPS per-user:    198.4 tok/s/user  CI [197.9, 198.9]
  ...
The tension this creates. If the only long-enough plateau is a later, degraded step, it gets reported (with the skip note) rather than the short healthy one — the duration requirement wins. The plateau_index / skipped_short metadata keeps that honest, and a consumer that prefers the first healthy plateau can read them and decide.

Only when no admissible plateau is long enough does the run report not found, naming the longest candidate:

=== STEADY STATE (headline) ===
  not found: all 6 admissible plateau(s) too short: longest 15s < 600s required (floor-dominated); pass --no-min-duration to override

--no-min-duration disables selection-time enforcement: the first plateau is reported as usual, with a "Window too short" advisory when it is below min_duration.

=== STEADY STATE (headline) ===
  window: super-passes 0..3 (post-warmup), 1600 samples
  TPS per-user:    199.6 tok/s/user  CI [198.7, 200.5]
  TPS system:   174112.3 tok/s        CI [149863.2, 198361.4]
  ...
  WARNING: Window too short -- 3s steady vs 600s desired (floor-dominated); the steady number is a best-effort estimate over too little wall-time

Either way the full breakdown (window_duration_s, min_duration_s, dominant term, k*, CoV_b, τ_sp, L_p90) is in the JSON under steady_state.short_window.

10 · End-to-end worked example

A real high-concurrency run — gpt-oss-120b, C=7168, ~633k system TPS (13 GB events.jsonl):

StageResult
Bucket70 super-passes (size 6396), warmup = 1 → 69 post-warmup
Gate + segmentone plateau, super-passes 0–68 (the whole run). TPOT is flat (tpot_p50 9.58 ms → p99 9.95 ms), so no break. TTFT is not gated: its tail is huge and spread (p50 1274 ms, p90 4286 ms) but doesn't fragment the window.
Throughputper-user 104.3 tok/s (CI [104.1, 104.7]); system 633 262 tok/s (CI [624k, 642k])
Min-durationCoV_b≈0 → k*=4 (floor) → T_precision exempt; floor 600 s binds. Whole-run offered span = 853 s ≥ 600 s.
VerdictFOUND 853 s of steady TPOT. Plus a soft WARNING: ttft_p90 … drifting UP — TTFT climbs across the run (queue building), surfaced but not fatal.

Under the earlier all-metric gate this same run was rejected: TTFT-tail noise chopped the 853 s plateau into 10 pieces (longest 123 s < 600 s). Gating on TPOT — the metric that is actually steady — recovers it. A run does still reject when its whole-run offered span can't reach the floor, or (like DeepSeek-R1) when relaxation demands tens of minutes it doesn't have.

On synthetic runs with planted plateaus the detector recovers the true steady TPOT to within 0.1% at up to 1.64M TPS (see §11).

11 · Validation sweep

The min-duration formula and the detector were calibrated against a synthetic throughput × concurrency sweep — planted steady plateaus at known service rates, spanning ~1k to ~3.3M output tok/s. Findings:

  • Accuracy. Wherever a genuine steady region exists, the detector recovers the planted steady TPOT to <0.1%, validated up to 1.64M TPS on 550k-sample runs (no memory/time blowup).
  • The ramp-trap. When n_samples ≈ concurrency, each slot issues ~1 sample and the run never leaves the ramp; the naïve gate reports a confident but ~3× wrong steady value with found = true. The duration floor (600 s vs a <2 s wall) is exactly what rejects it.
  • Regimes. Floor binds for clean/fast runs, relaxation for long-tail (a reasoning workload needs tens of minutes), precision for noisy metrics (agentic).
