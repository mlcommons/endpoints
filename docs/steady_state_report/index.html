Steady-State Windowing

Recovering the steady-state number from a benchmark run — across concurrency, offline (max-throughput), and poisson load. Interactive: the detector re-runs live on real events.jsonl-derived series as you move the sliders.

1. The problem

A benchmark run's reported number is contaminated by non-steady regions: a ramp-up (filling the pipe / queue reaching equilibrium / a fill-burst queueing) and a ramp-down / drain (in-flight finishing after issuance stops, plus long-OSL and slow-rank stragglers). Averaged over the whole run, these deflate throughput and inflate tail latency. The goal is per-run steady-state correctness — report what the system sustains in steady state, not the run-length average — while measuring only over whole dataset passes (no partial-pass OSL bias).

The deflation is real and scales with load: e.g. offline run 293038 reports 191 req/s over its full 156 min but sustains 279 req/s in steady state (a 31% undercount from a 60-min straggler tail); concurrency c22528 reports a 15.7 s p99 TTFT that is really 2.5 s once the fill ramp is cropped (−84%). Move to §3 to see this on the data.

2. Strategies — methodology, math, risks

Concurrency — issue-time super-pass window + adaptive warmup + per-metric drift

Methodology. Bucket samples by issue order into super-passes of S = ceil(N / dataset_size) dataset passes (enough issuance to hold N distinct samples in flight). The measured set for a window [start, end) is every request issued in that span; throughput denominator = issue-time span last_issue − first_issue (drain lives after the last issue, never entering the denominator), while latency percentiles use the full lifetime of that same set — one membership set, so throughput and latency can't disagree.

Adaptive warmup (band). steady = median(p99 TTFT over the back half); drop leading super-passes while value > steady·(1 + band). Band-based (not slope) so a single settling outlier can't collapse the crop, and only HIGH leading values are dropped.

Per-metric drift. OLS fit over the post-warmup per-super-pass series; rel_drift = slope·(n−1)/median, snr = |slope·(n−1)| / stdev(residuals). Drift iff |rel_drift| ≥ 0.15 ∧ snr ≥ 2.0; drifting_up (pathological — no steady state) vs drifting_down (residual settling) vs steady.

CoV ensemble. CoV = σ/μ (population stdev / mean, unitless) of a metric's per-super-pass percentiles across a trailing window; converged when CoV < bound for every metric. Run a 6-detector ensemble (window,bound) ∈ {(3,.03),(3,.05),(4,.05),(5,.08),(6,.10),(6,.15)}; 0/6 converged ⇒ no steady state.

Risks & mitigation. p99 TTFT has no steady state (drifts up) → flagged drifting_up rather than reporting a false number. Metrics settle at different rates → the slower one reads drifting_down (transparent, not a false alarm; follow-up: per-metric warmup). CoV noise floor: each super-pass p99 is ~256 tail samples, so bounds ≤0.02 never converge — hence the ensemble of bounds. Settling outlier → band + back-half median is robust.

Offline (max-throughput) — completion-rate plateau-edge

Methodology. Issue time is degenerate (all at t=0), so bin completions by completion time and work on the completion-rate series. The plateau is the longest contiguous run of bins with lo ≤ rate ≤ hi, lo/hi = median·(1∓band), band = 0.10. Its start = end of the leading ramp/settle; its end = drain-onset. Report the plateau rate. No dataset-boundary snap — a rate over the plateau reflects the steady ISL/OSL mix, so there's no sample-set to bias.

Risks & mitigation. Variable ramp shape (settle-down vs ramp-up) → the longest-in-band run is shape-agnostic (verified on both 293038 & 272936). Second-issuance blip (a late extra pass) → falls after drain-onset, outside the run, ignored. Tail-heavy plateau (tail bins > plateau bins) → median mis-centers the band; switch the steady estimate to an upper quantile/mode. Non-streaming ⇒ no TTFT; throughput only.

Poisson — the concurrency tool, unchanged (pass-unit)

Methodology. Poisson issues over time in dataset passes, so it is the concurrency algorithm with N undefined ⇒ S = 1 (one pass per super-pass). The adaptive warmup crops the queue-fill ramp; the per-metric drift test runs on per-pass TTFT/latency. Throughput = offered qps (fixed); latency is the metric of interest.

Risks & mitigation. Under-saturated (232386 @ 37 qps): genuinely steady, ~3-min drain — nothing special needed. Near saturation: poisson backlogs like offline; detect it (completion rate falling below offered rate) and add the offline plateau-edge. Untested — needs a near-saturation run.

4. Long-running samples, the backlog tail & metric selection

DSR1 and agentic datasets contain a small subset of very-long-OSL samples (DSR1 long-CoT up to max_new_tokens=20000; the agentic set OSL p50 99 / p99 2355 / max 11457 — a ~115× spread). Issued repeatedly (K passes under concurrency, or an offline burst), each long sample takes far longer than one pass, so copies of the same long samples [L₀…Lₙ] from many passes accumulate — and under temperature-0 decoding the re-issued copies produce the same long output. The drain tail is then many repeats of the same handful of long samples backlogged behind everything else (offline 293038: a ~60-min tail of these vs an ~80-min plateau).

Verified (232386, DSR1 poisson, 140k samples): e2e latency p50 26.5 s / p99 181 s (6.8× skew) — but TTFT p50 0.22 s / p99 0.50 s (2.3×, tight). The long generation inflates e2e latency and OSL yet leaves TTFT and TPOT decoupled (per-request / per-token).

How the window handles it. The window is defined on issue membership: a sample counts iff it was issued in the window, and we aggregate its full lifetime — including completions that land far later in the drain. We do not re-define the window by completion time and do not wait for all issued samples to finish. So e2e latency and OSL for the window are skewed by the backlogged long samples and are not trustworthy steady numbers; TTFT and TPOT are not skewed and remain valid.

Proposal — LLM metric selection. Report the steady state with token-based, OSL-robust metrics: TTFT, TPOT, and TPS (output tokens/s), and drop QPS (requests/s). With OSL varying ~100×, a "request" is not a unit of work (QPS conflates a 10-token request with a 10000-token one); tokens/s (TPS) is the meaningful throughput. e2e latency / OSL become context, not headline steady metrics. Token-free, uniform-work loads (e.g. text-to-video) keep a request/sample-rate throughput. We do not drop the long samples (they contribute tokens to TPS and matching TTFT/TPOT) — we drop reliance on the skewed metrics.

In §3 above, QPS is retained for illustration but flagged deprecated-for-LLMs; TPS is the intended replacement (requires regenerating report_data.js with token counts — a follow-up).
