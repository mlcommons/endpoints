Steady-State Windowing — experiments & methods

For an LLM benchmark run: when and where a steady state exists, how to stabilize or measure it, where each method fails and how we mitigate, and the effects on runtime and on the numbers we report. Grounded in three experiments over real events.jsonl corpora (concurrency C8 → C22528, DeepSeek-R1 ~28k, poisson). The detector in §7 re-runs live in the browser.

1. The problem

A run's reported number is contaminated by two non-steady regions. Ramp-up: at t=0 the client fills the pipe — under concurrency it issues a fill-burst of N requests that queue against a finite-rate server, so time-to-first-token (TTFT) spikes, and the spike grows with N. Ramp-down / drain: after issuance stops, in-flight decays below N and the remaining requests finish late. Averaged over the whole run these deflate throughput and inflate tail latency. The goal is per-run steady-state correctness — report what the system sustains, not the run-length average — measured over whole dataset passes so no partial pass biases the ISL/OSL mix.

This report is organized as four questions: §2 when/where a steady state exists, §3 how to stabilize the curves (feathered starts), §4 how to measure them (issue-time window, guarded tail-cut, CoV+trend), §5 failures & mitigations, and §6 effects on runtime and reporting.

When & where
2. Is there a steady state to find?

Not every run contains a windowable steady region, and the answer depends on the load mode. The unit of measurement is the super-pass: S = ceil(N / dataset_size) dataset passes — the minimum issuance to hold N distinct samples in flight — so every window contains a representative full-dataset workload mix even when dataset_size < N. Samples are bucketed by issue order.

Coverage status — classify before windowing (never hard-fail)

status condition behavior
windowable ≥ warmup + 1 full super-passes drop warmup super-pass(es), window the rest
insufficient_passes ≥ 1 pass but < warmup + 1 super-passes best-effort over all super-passes, low confidence
partial_dataset < 1 full dataset pass best-effort over a biased ISL/OSL subset — unreliable

Example: C8 (concurrency 8, 2226 issued < 6396 dataset) has only super-pass 0 — not windowable; the number is the raw measurement, flagged. High concurrency is where the correction matters and where runs naturally accumulate many super-passes.

Per load mode

Concurrency — in-flight is pinned at N

In-flight is held at N by construction, so the ramp boundaries are knowable and issue-rate = completion-rate across the steady span. This is the primary mode for the correction.

Offline (max-throughput) — issue time is degenerate

All queries are issued at t=0, so bin completions by time and find the plateau — the longest contiguous run of in-band completion-rate bins. Its start = end of the leading ramp; its end = drain-onset. Report the plateau rate.

Poisson — the concurrency tool with S = 1

Poisson issues in dataset passes with N undefined ⇒ one pass per super-pass. Under-saturated poisson is genuinely steady; near saturation it backlogs like offline and needs the plateau-edge (untested — needs a near-saturation run).

When there is no steady state

If p99 TTFT keeps climbing across super-passes, there is no steady state to report. The trend test flags drifting_up (pathological) rather than emitting a false point estimate — see §5. This is a first-class outcome, not an error.

The drain-tail (“hairball”) is structural — and exists in every mode

The dataset is always issued in full, without replacement, repeating across passes. So in every load mode a hairball of long-lived requests accumulates toward the end — long-OSL samples that, re-issued each pass, trail behind everything else. What differs is how much:

  • Concurrency — the tail is exactly the N in flight when issuance stops (|tail| == N at every point; Experiment 1). A random issue-time snapshot, not the slow tail.
  • Max-throughput / offline — a seconds-long t=0 issue burst, then the whole run is drain: the long-OSL backlog builds up over the entire run. This is the mode where the correction matters most.
  • Poisson — QPS gating throttles arrival, so the backlog barely accumulates; the hairball is smallest.

Verified on three DeepSeek-R1 Hecate runs (issue burst vs drain, and the dataset_idx concentration of the late completions):

mode / run issue span drain drain / total distinct dataset samples in last 5% of wall-clock
poisson 232386 63 min 2.4 min 3.7% 3178 (spread — no hairball)
offline 272936 9.2 s 81 min 99.8% 767, re-issued ≤14×
offline 293038 34.5 s 152 min 99.6% 844, re-issued ≤18×

Offline is almost entirely drain — the last 5% of wall-clock is a concentrated hairball of ~800 specific long-OSL dataset samples (of 4388) each re-issued up to 18×, provable via dataset_idx. Poisson spreads its late completions over ~3200 distinct samples — the QPS gate stops any pile-up. So the hairball is universal but the windowing response differs: concurrency crops the warmup and cuts the guarded tail; offline reports the completion-rate plateau (§2) rather than a “cut” — the drain is the run.

Verified against the per-sample data, the tail decomposes into two parts: last-issued requests (issued just before stop — normal, short) and the hairball (long-OSL requests issued far earlier that are still running — the very long tail). Splitting each tail at one steady-median lifetime of issue-lead:

point (concurrency) N = |tail| last-issued hairball hairball reaches
C1024 (gpt-oss) 1024 958 66 (6.4%) life 10.9 s, issued 10.8 s pre-stop
dsr1 ~28k* (reasoning) 28080 11 678 16 402 (58%) life 963 s, issued 956 s pre-stop

|tail| == N exactly (concurrency). The hairball is a 6% sliver for gpt-oss (near-uniform OSL) but dominates the tail (58%) for the reasoning model, reaching requests issued ~950 s before issuance stopped — the long-CoT stragglers, the same samples re-issued each pass and left behind. * DeepSeek-R1 point is config-less (N, S, dataset assumed) — tentative. The dataset_idx column (from sample_idx_map.json) lets a study confirm the hairball is the same handful of long dataset samples across passes; populated for runs whose index map is available.

How — stabilize
3. Feathered starts: flatten the ramp-up spike

The fill-burst is avoidable. Today's issuance shocks the server at t=0: ConcurrencyStrategy builds a semaphore with N permits (strategy.py:276) and the first N acquire()s fire with no intervening completion (:281), so N requests hit the queue at once; BurstStrategy self-rechains with no delay (:238), draining the whole pool near t=0. A staged ramp — issue N/S at a time at a critically-damped interval step/prefill_rate — replaces the one tall spike with S small teeth.

How it's implemented, and the resulting behavior

The change is timing only — the sample order is untouched; requests are still drawn from sample_order in the same sequence, just released in S increments instead of all at once.

Concurrency. Today the gating semaphore is built already full with N permits, so the first N acquire()s pass through instantly. The staged variant builds it empty and a ramp task grants step = ceil(N/S) permits every step_interval until N are out; completion-driven release (one permit per completion) is unchanged. In-flight therefore climbs as a staircase step → 2·step → … → N and then holds at N, instead of jumping to N at t=0. 

# UNMERGED sketch — illustrative, not wired into strategy.py
class StagedConcurrencyStrategy:
    def __init__(self, target_concurrency, sample_order, loop, *, steps, step_interval):
        self._target        = target_concurrency
        self._per_step      = math.ceil(target_concurrency / steps)
        self._step_interval = step_interval
        self._sem           = asyncio.Semaphore(0)   # start EMPTY, not full

    async def _ramp(self):
        granted = 0
        for _ in range(self._steps):
            n = min(self._per_step, self._target - granted)
            for _ in range(n):
                self._sem.release()          # admit one step's worth
            granted += n
            if granted >= self._target: break
            await asyncio.sleep(self._step_interval)

Max-throughput is the same idea without completion-driven replacement: issue step, wait step_interval, repeat until the pool is exhausted.

The interval is the whole game. The server admits first-tokens at a finite prefill_rate; a step of step requests takes step / prefill_rate to drain the prefill queue. Setting

step_interval ≈ step / prefill_rate = target / (S · prefill_rate)

lets each increment's queue drain before the next arrives, so the queue never grows past one step. That is why the peak first-token wait drops from target/prefill_rate (burst) to (target/S)/prefill_rate — the S× reduction — while the total fill span stays target/prefill_rate (near-Pareto: same fill duration, S× smaller spike). Since prefill_rate isn't known a priori, the recommended interval is drain-driven: advance when the current step's requests have all reached first token (needs no constant), falling back to a probe-measured or fixed wall-clock interval.

Where it helps, where it doesn't.

Concurrency: adopt, S = 4–8 (S=4 captures most of the benefit; beyond S≈8 diminishing returns). It is complementary to the super-pass warmup crop, not a replacement — staging is timing, the crop is issue-order; orthogonal. Max-throughput: staging is largely moot — a saturating burst has no steady baseline, and staging only lengthens the issue span. The staged strategy variants are unmerged sketches in the design doc; nothing in strategy.py is changed yet.

How — measure
4. Windowing, the guarded tail-cut, and CoV+trend

4.1 The issue-time window

Define the window on issue time, not completion time, with one membership set for both metric families. Measured set = every request issued in [sp_start, sp_end). Throughput denominator = the issue-time span last_issue − first_issue (the drain lives after the last issue, so it never enters the denominator — no end-crop needed). Latency / token percentiles use the full lifetime of that same set. One set, so throughput and latency can never disagree on what they measured.

4.2 Cutting the drain-tail — safe, but guard it

Experiment 1 measured the drain-tail (the N in flight at issuance-stop) against the steady set. Its per-token latency (TPOT) is actually faster than steady — concurrency collapses N→0 during drain, so decode de-contends. Cutting it therefore nudges reported TPOT p50 up only 0.4–1.1% (the conservative direction), leaves latency tails within 0.32%, and does not move throughput at all.

The guard: TPOT-invariance is observed, not guaranteed.

The safety of the cut rests on the tail sharing the steady TPOT distribution. That held across this static corpus, but it is a property of a healthy run, not an invariant — a server hiccup, thermal throttle, or cache eviction during drain could make the tail genuinely slower. So the cut must be a guarded rule, not an unconditional one:

cut_tail iff KS/effect-size(tail.TPOT, steady.TPOT) is small AND tail.TPOT.CoV not inflated; else keep the tail (or flag drifting).

When the guard fails, the tail carries real signal and must stay in the window. This is the encoded criterion: only cut when the invariance the study observed actually holds at runtime.

4.3 Finding the window edge — CoV must be gated by a trend test

The coefficient of variation (CoV = σ/μ) of a metric's per-super-pass percentiles across a trailing window declares convergence when it drops below a bound. Experiment 3 stress-tested it: CoV alone is not trustworthy. Where p99 TTFT is still drifting, the rule happily “converges” on a window that is 20–70% off the asymptote — converged ≠ accurate.

What CoV is, and how it's measured

The coefficient of variation is relative spread:

CoV = σ / μ  (population standard deviation ÷ mean, unitless)

It is measured per metric, over a trailing window of W super-passes. Take one scalar percentile — say p99 TTFT — collapse each super-pass to that single number, then compute σ/μ over the last W of them. A small CoV means the metric has stopped moving relative to its own level; the window is declared converged when CoV < bound for every metric in the ensemble (p50/p99 of TTFT and latency). Being unitless is the point: it puts a 1 s TTFT and a 20 s latency on the same “how steady” scale, so one bound governs them all.

It is computed in four steps (worked below on real C1024 data): (1) the whole timeline of per-sample TTFT; (2) segment by issue order into super-passes — here S=1, so one super-pass is one 6396-sample dataset pass; (3) aggregate each super-pass to a single scalar — its p99 TTFT; (4) take CoV = σ/μ over the trailing W of those per-super-pass p99s.

Step 4 — the calculation. CoV over the trailing W=5 per-super-pass p99s (bound 0.05), contrasted with a run where the same rule is fooled:

run trailing window (p99 TTFT, s) μ σ CoV verdict
C1024 1.143, 1.148, 1.066, 1.126, 1.117 1.120 0.029 0.026 converges — correct
C7168 8.241, 8.338, 8.628, 8.280, 8.054 8.308 0.186 0.022 converges — 24% low

Both windows have CoV < 0.05, so the rule stops on both. For C1024 that is right — the series really is flat at ~1.12 s. For C7168 it is a trap: those five super-passes are locally flat, but the series keeps climbing to an asymptote of ~10.96 s, so the chosen window sits 24% below the true steady value. Low CoV certifies local stability, not global convergence — which is exactly why the trend gate (below) is mandatory.

Recommended defaults (Experiment 3).

(1) Never trust CoV alone — gate every verdict with the trend test (drift.classify_run); if a reported metric is drifting_up, report drift, not a point estimate. Mandatory, not advisory. (2) trailing window ≥ 4–5 (not the shipped 3) with bound 0.03–0.05. (3) keep p99 and both TTFT + latency in the ensemble (p50-only / latency-only converge 100% of the time but at the worst error). (4) treat ensemble concordance < ~0.8 as a drift guardrail (it tracked the bad points: C22528 0.62, dsr1 0.00).

Failures
5. Failure points & mitigations

failure point symptom mitigation
TPOT-invariance breaks mid-run (server anomaly) drain-tail genuinely slower than steady → cut biases TPOT guarded cut (§4.2): only cut when tail≈steady TPOT holds; else keep/flag
CoV trusted alone on a drifting metric “converges” on a window 20–70% off mandatory trend gate; window ≥4–5; concordance <0.8 guardrail
p99 TTFT never plateaus no steady state exists flag drifting_up — refuse a point estimate, don't fabricate one
Metrics settle at different rates slower metric reads drifting_down transparent (not a false alarm); follow-up: per-metric warmup
Reasoning-model long-OSL tail (dsr1) cut discards longest-OSL requests wholesale (tail OSL 3.4× steady) cut still TPOT/latency/throughput-safe; report OSL coverage separately
Tail-heavy offline plateau median mis-centers the in-band plateau switch the steady estimate to an upper quantile / mode
QPS on a ~100× OSL spread a “request” is not a unit of work report token-based metrics (see §6): TTFT, TPOT, TPS; drop QPS for LLMs

On runtime — staging

A staged ramp front-loads (S−1)·step_interval of wall-clock before steady state. It does not shorten the ramp (server-rate-bound), so it costs a little runtime to buy a flatter spike. Budget it; do not expect it to shrink the passes the warmup crop must drop.

Reconciling “throughput bias”

Two framings look contradictory but agree. Cutting the tail perturbs the issue-based QPS by 0% (tail completions were never in the numerator). Separately, the issue-to-issue denominator is +13% (dsr1) shorter than a complete-based one — but that is the intended drain exclusion, the whole point of measuring on issue time. Both say the same thing: the tail-cut is safe and the issue-to-issue denominator is the right one.

Metric selection for LLMs.

With OSL varying ~100×, report the steady state with token-based, OSL-robust metrics — TTFT, TPOT, and TPS (output tokens/s) — and drop QPS; e2e latency / OSL become context, not headline steady numbers. We do not drop the long samples (they contribute tokens to TPS and matching TTFT/TPOT); we drop reliance on the skewed metrics. Token-free uniform-work loads (e.g. text-to-video) keep a request-rate throughput.
